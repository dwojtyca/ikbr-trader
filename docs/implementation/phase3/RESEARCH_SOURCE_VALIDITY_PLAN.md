It has no invented future expiry, no automatic 48-hour renewal, and no claim that a provider guarantees future access. Preserve finite historical records exactly. The owner confirmation authorizes a new ongoing policy for the already-established issuer, endpoint, metadata and paid-access identities; it does not recreate or rewrite their original evidence.

Legacy 900000 policies remain readable and retain their original behavior. Marketaux remains on-demand with 1800000 ms news freshness, 900000 ms slots, complete two-pass coverage, configured finite capacity and the pooled 2400/day allocation under paid 2500/day entitlement. No per-signal fetch, provider-probing service, new cache, cross-manifest evidence reuse, quota reset, scheduling change, or broker-accounting qualification change is included.

Actual permission denial, revoked access, wrong identity, changed WSH metadata, malformed data and unresolved acquisition/publication remain failures. Existing hard-failure invalidation must defeat a previously usable calendar. Owner confirmation is not an override for a negative provider response or an unknown result. WSH transient refresh failures retain only the exact already-proved current-manifest calendar within its original TTL, as accepted in the [freshness/recovery plan](WSH_FRESHNESS_RECOVERY_PLAN.md).

## Exact configuration union

The existing source adapter/parser kinds and top-level manifest schemaVersion stay unchanged. Each qualification and entitlement record independently accepts exactly one of two shapes:

1. **Legacy finite**: all current keys, `expiresAt` a valid finite ISO instant, and no `validity` property. Preserve current structural/order checks, original meaning and hash. Equality at expiry remains unavailable. Do not inject defaults or serialize a discriminator into old parsed objects.
2. **Operator-confirmed ongoing**: all current keys, `expiresAt: null`, and exactly one additional property:

```json
{
  "validity": {
    "mode": "OPERATOR_CONFIRMED_ONGOING",
    "confirmedAt": "<actual captured/recorded owner-confirmation instant>",
    "confirmationRef": "<non-secret audit reference>",
    "confirmationHash": "<SHA256 of the private confirmation receipt>"
  }
}
```

The new object has exactly those four keys. `confirmedAt` is a finite valid instant, no earlier than the original validFrom (WSH) or verifiedAt (Marketaux), and must be <= the time being validated for use. `confirmationRef` is a nonempty bounded audit identifier (1–200 ASCII letters/digits plus `. _ : / -`, starting with a letter or digit), with no query, credential or arbitrary diagnostic payload. `confirmationHash` is lowercase64-hex. The private confirmation receipt records the actual owner statement and the instant it was captured/recorded for this policy (never an invented message-send time when unavailable), relevant provider/source/issuer identities, original evidence references, operator policy scope and any known actual subscription limit; its hash/reference are part of the new canonical manifest. Neither a source success nor a timestamp alone manufactures this confirmation.

Require null exactly for ongoing. Missing expiresAt, undefined, string "null", null without the discriminator, unknown discriminator, extra keys, invalid/future confirmation, malformed reference/hash and a finite expiry combined with ongoing are rejected. Keep Marketaux outcome semantics: ongoing with UNVERIFIED does not grant access. Keep source automation/retention and all issuer/conId/ISIN/endpoint/metadata/budget checks unchanged. Mixed finite/ongoing qualification and entitlement are allowed; the finite member still caps use. When an actual finite provider/permission termination is known, represent it with the finite form; do not select ongoing to evade that known limit.

Original qualification IDs, endpoint ownership reference, metadata hash, Marketaux entity crosswalk, original verifiedAt/validFrom, receiptHash/evidence URLs, and entitlement terms/paid limits remain truthful. Ongoing confirmation is a new policy decision about continued use of that established evidence, not a claim it was re-fetched. Changed issuer/account ownership, endpoint qualification, conId/entity or metadata requires the existing explicit requalification process; paid status alone cannot qualify a different identity. Access revocation is handled by existing denied-source policy/adoption or actual hard provider failure, not silently auto-renewed.

## Deadline API and serialization

Introduce one small shared source-validity helper/types module (for these two adapters only), with strict record-shape validation and a function that evaluates the selected policy at a supplied finite time. Its result is `number | null`: an actual finite policy deadline, or null for ongoing. `wshQualificationDeadline(config, now)` and `marketauxQualificationDeadline(config, now)` adopt that return type; they return the minimum finite member when mixed, null only when both are ongoing, and throw the existing adapter qualification-unavailable reason for an ineffective policy. Existing invalid schema reasons remain adapter-specific; preserve sanitized original causes at failure boundaries.

Every caller handles null explicitly. Acquisition/call deadlines continue to be `min(existingFiniteOperationBound, finitePolicyDeadline)` where a finite policy exists, otherwise the unchanged finite operation bound. Never pass null to Math.min/Date.parse/researchTime, emit Infinity/NaN, or construct an unbounded Date. In-memory Infinity is not needed by this contract. WSH35s attempt/30s acquisition/<=10s call, existing monotonic bookkeeping caps, cleanup bounds and Marketaux120s total/call/byte caps remain unchanged. A host-clock rollback cannot replace the already-accepted absolute monotonic budget.

Successful source data always has a finite data expiry. WSH diagnostic expiry is original checkedAt+configured maxAge capped only by actual finite policy deadlines; Marketaux remains checkedAt+1800000. Overall eligibility/binding expiry remains the minimum of original finite data/report deadlines and any finite policy deadlines. There is no null/unbounded eligible AI binding. The helper may need a separate structural deadline read for diagnostics, while use-time validation still rejects future policy confirmation; diagnostics must never turn invalid policy into READY.
