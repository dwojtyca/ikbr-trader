# WSH hourly regular refresh

Status: ACCEPTED by independent critical reviewer `stale_alert_plan_review` (gpt-6-astra/high), after one SQL identity clarification repair. Implementation requires a different final reviewer. Owner direction, 2026-10-15: ordinary WSH refresh every hour, successful calendar usable for 24h, existing bounded 30s/120s recovery unchanged. Author requested/actual model: gpt-6-astra/high. This document authorizes no provider calls, private configuration edits, deployment or trading activation. It supersedes only the regular 15-minute setting in the [freshness/recovery plan](WSH_FRESHNESS_RECOVERY_PLAN.md); that plan's accepted safety and review repairs remain normative.

## Outcome and scope

Support exactly `refreshIntervalMs=900000` for existing manifests and `3600000` for a newly adopted hourly manifest. Preserve old canonical JSON and hashes. Existing 15-minute sources retain their original cadence and either already-supported age 900000 or 86400000. The new hourly operational configuration uses `maxAgeMs=86400000`; support only that age with the new hourly interval, avoiding an unrequested 15-minute TTL/hourly-refresh combination. Missing fields, strings, fractional values and other intervals remain invalid. No implicit conversion of old configurations and no arbitrary interval range.

“Hourly” means at least 3600000ms between ordinary cycle starts, measured by database time; it does not mean starting at every wall-clock hour boundary or catching up missed hours. A delayed cycle starts once when eligible and establishes its own next regular deadline. Retries do not move that deadline. This changes acquisition cadence, not evidence timestamps, 24h age, qualification/entitlement expiry, provider coverage or AI binding.
